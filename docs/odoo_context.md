## Known Issues / Open Risks

**Unresolved migration conflict (blocker).** `supabase/migrations/20250101000000_auth_setup.sql` and `supabase/migrations/20260822060408_initial_dayflow_schema.sql` both issue a bare `CREATE TABLE public.profiles` and `CREATE TABLE public.employees`, with different column constraints, and both define RLS policies named `profiles_update_own` and `employees_select_own_or_admin` with different logic. Applying both files in order to a fresh database fails. This must be resolved (merge/rewrite the two files into one lineage) before any further migration or `supabase link`/`push` work.

**Non-idempotent DDL.** Every `CREATE TRIGGER`, `CREATE INDEX`, `CREATE POLICY`, and `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` statement in both migration files is written in its plain, non-idempotent form (no `OR REPLACE`, `IF NOT EXISTS`). Only `CREATE OR REPLACE FUNCTION` statements are idempotent. Re-running either migration file against a database where it already ran will error.

**Two incompatible, coexisting auth implementations.** A real Supabase-backed auth stack (`AuthContext.tsx`, `auth.service.ts`, `LoginPage.tsx`, `SignupPage.tsx`, `ProtectedRoute.tsx`, `RoleRoute.tsx`) exists alongside a mock/`localStorage`-backed one (`auth-context.tsx`, `sign-in.tsx`, `protected-route.tsx`). Only the mock stack is mounted in `App.tsx`. Both define exports named `AuthProvider` and `useAuth` from different `React.createContext` instances. If anyone imports the real `ProtectedRoute`/`RoleRoute`/`LoginPage`/`SignupPage` into `App.tsx` without also swapping the mounted `AuthProvider`, the app will compile fine (`tsc --noEmit` passes on both stacks today) but crash at runtime with `useAuth must be used within AuthProvider`, because the real `AuthContext.tsx` context object is never provided anywhere in the currently-mounted tree.

**Duplicate type-definition sources.** `src/types/index.ts` and `src/types/domain.ts` both independently model the same 7 DB tables (`Profile`, `Employee`, `AttendanceRecord`, etc.). They currently agree column-for-column with the migration schema, but there is no single source of truth — a future schema change has to be applied in two places by hand.

**Minor: swallowed errors in the orphaned real auth context.** In `AuthContext.tsx` (currently unreferenced from the live app), two direct calls — `supabase.auth.getUser()` (used in `refreshUser()`) and `supabase.auth.getSession()` (used in the init effect) — destructure only `data` and discard `error`, unlike the rest of the file which consistently runs errors through `mapSupabaseError`. Low impact today since it's not wired in, but should be fixed before this file is adopted.

**Signup route not registered.** `src/routes/paths.ts` has no `signUp` entry, and `App.tsx` registers no route that renders `SignupPage.tsx`. The live sign-in page's copy ("New employees are added by HR/Admin — you'll receive a Login ID and temporary password.") suggests self-serve signup may be intentionally out of scope for this product's login model, not just unfinished — flagged as a fact for the team to confirm, not a recommendation either way.

**Phase 6 not started.** No profile backend service exists. Nothing to audit further here.

## Integration Status

- **TanStack Query**: wired into `App.tsx` via `QueryClientProvider` (`src/lib/query-client.ts`), and every feature folder (`employees`, `attendance`, `leave`, `payroll`) has real `useQuery`/`useMutation` hooks in its `hooks.ts`. However, every one of those hooks calls into `src/lib/mock/db.ts` — none of them call Supabase.
- **React Router**: wired into `App.tsx` via `BrowserRouter`, with guest/protected/role-gated route groups already structured around `paths.ts`.
- **Supabase client**: correctly constructed (Phase 1), but not called anywhere in the code path the app actually renders. A full-repo search found only 4 files that reference `supabase` at all (`client.ts`, `lib/supabase/auth.ts`, `auth.service.ts`, `AuthContext.tsx`) — the last three of which are not imported from `main.tsx`/`App.tsx`.
- **Live data source**: 100% mock. All auth, employee, attendance, leave, and payroll data currently comes from `src/lib/mock/db.ts` and its companions (`seed.ts`, `people.ts`, `random.ts` — ~1,300 lines total, zero Supabase references). The sign-in page even ships hardcoded demo credentials (e.g. `OIANVE20200001` / `Admin@123`).
- **Password reset flow**: the live `forgot-password.tsx`/`reset-password.tsx` pages don't call mock or real backends at all — `onSubmit` is a bare `setTimeout(500ms)` UI simulation.
- **Broken imports**: none. `npx tsc --noEmit` exits clean (0 errors) across the entire `src` tree, including the orphaned real-auth files — they are unused, not broken.
